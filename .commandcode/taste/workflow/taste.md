# Workflow

- Expects the agent to actually launch/serve the app locally itself (e.g. `npm start` in the background) and hand back ready-to-use localhost URLs plus login credentials, rather than just telling them which commands to run. Also manages the process lifecycle this way: a bare "restart app" (no commands, no port/PID) is expected to mean kill the existing process and bring it back up without further questions. Confidence: 0.7
- Prefers the agent to verify a service is really up (HTTP status/redirect checks per route) before declaring it running. Confidence: 0.55
- Wants recommendations grounded in a full-codebase audit rather than guesses: expects the agent to actually scan routes/views/services and cite concrete file/line evidence before proposing changes, based on the codebase's real current state rather than assumptions. The same applies to open-ended review asks ("coba cek apakah ada yang perlu di fix? atau ada alur yang salah?"): wants a severity-prioritized list of concrete defects (P0 money/security first, then P1, P2), each with file:line, impact, and suggested fix, plus a short "already safe" section so he doesn't worry needlessly — delivered before any code is modified. Confidence: 0.6
- Prefers a plan/recommendation first and gives explicit approval before the agent executes structural changes; expects the agent to wait for a go-ahead and offer to proceed stage-by-stage, and approves with a terse "oke" — or by naming the chosen option ("opsi A aja") when the agent presented labelled alternatives — which then lets the agent run large multi-file refactors hands-off without further check-ins. Confidence: 0.65
- Prefers adopting work from another branch feature-by-feature instead of a wholesale merge ("di main ada update... mana yang bisa di ambil"): wants the agent to diff against the current branch, separate real content changes from noise (e.g. CRLF-only rewrites), list what can be taken as-is vs. what must be merged by hand hunk-by-hunk, and flag that the feature must be taken as a coherent whole (with its deps/config defaults). He approves that selective-take plan in one word ("ambil") rather than asking for a real merge. Confidence: 0.55
- Treats a reported bug as a class of bug: expects the fix to cover every page/route that shares the same code path, not only the page he pointed at. He re-tests the sibling surfaces himself and comes back with a terse "ini masih" plus a screenshot if any one of them still shows the old behavior (e.g. after the customer dashboard payment modal was fixed, he retested `/customer/voucher` and reported it separately) — so it pays to sweep the other routes/views for the same pattern in the same pass and report the remaining spots.
- When approving a risky/tuning change, pairs the go-ahead with a risk check ("gas tapi ada bakal masalah gak?") — expects the agent to name the concrete failure modes/side effects (e.g. false "Offline" flags) and the mitigations, and will proceed once risks are bounded. Confidence: 0.5
